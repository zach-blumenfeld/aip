# Changelog

All notable changes to AIP are documented in this file.

Since `0.7.0` the runtime (the `agent-instruction-protocol` distribution, the `aip` command and
package) and the format (`aip-spec`) live in this repository and release together under one
version, so there is one changelog; since `0.9.0` they are one package. From `0.4a0` to `0.6a1`
the format had its own repository and changelog, and the two histories are interleaved below
with each section marked `(aip)` or `(aip-spec)`. Versions `0.3a3` and earlier predate the split
and cover both.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

The 0.9 release replaces the YAML procedure format with a text language, `procedure.aip`
(`docs/language/spec.md`). 0.8 skills do not load in 0.9 and there is no upgrade tool; the plan
is aip-dev#1. The milestones land one at a time below.

### Added
- **One skill, `aip`, and `make_procedure`** (plan K1).
  - **The `aip` skill replaces `aip-runtime` and `aip-compile`.** One page tells an agent how to find a procedure, run it, answer a pause (one task, or a batch of them by index), read an error, and write a procedure; the language is on one page beside it (`references/language.md`). `aip skill install` writes it into every agent detected on the machine (`aip skill install claude-code`, `codex`, or `--path DIR` for one), and removes the two old skills where an earlier `aip` installed them; `aip skill prune` removes old ones it has no record of; `aip skill list` and `aip skill remove` as before.
  - **`make_procedure` builds a procedure from a description.** `aip run make_procedure --inputs '{"name": "...", "description": "...", "materials": ""}'` hands the agent a task to write the program folder, with the language in the prompt; a script compiles what was written; and a loop hands the compiler's diagnostics back, up to five times, until the folder compiles. The result is the folder's path, its bundle id and any warnings left. When the folder compiles, its `procedure.aip` is left in the canonical form. It asks no decision model, so it runs on any machine with `aip`.
  - **It is in every catalog.** `make_procedure` ships inside the package as a bundle, and a server publishes it when it first starts, so `aip list` on a new store shows `make_procedure@1`. Its source is `examples/language/make_procedure/`.
  - **`aip upgrade`** publishes the procedures the package ships to the configured server, for a server that runs an older `aip` than yours (`Client.upgrade()` in the SDK). It takes no folder: the 0.8 command of that name, which rewrote a skill for a new format, has no successor.
- **`aip mcp`: the runtime as an MCP server** (plan M1; `docs/mcp.md`). An agent framework or a coding agent reaches procedures with the MCP client it already has: give it the command `aip mcp` (stdio), or run `aip mcp --http PORT` for streamable HTTP at `/mcp`. Six tools, each one SDK call: `search`, `describe`, `compile`, `run`, `resume`, `pull`. `run` and `resume` answer with exactly the object the command line prints (paused with its tasks, done with the result, or the error), as an ordinary result, so a pause or a refused answer never reaches the caller as an exception. Runs are recorded where `aip config` points, with the MCP client's own name as the `agent` (`aip runs --agent claude-code`; `aip mcp --agent` replaces it) and a `session` per call, per `--session`, or one per server. `examples/agents/mcp-smoke/run.py` is a client with no framework that runs `dynamic-policy` end to end. The package now depends on the MCP Python SDK (`mcp`).
- **`Client.resume(..., agent=, session=)`** in the SDK: who answers a pause, for the task's `answered_by`.
- **The console is in this repository, under `console/`** (plan C1). It is still the npm package `aip-console`, with its own version, its own changelog (`console/CHANGELOG.md`, which has what changed in it for 0.9: the card canvas, the 0.9 run record, drafts, the audit tab, the Studio removed) and its own release workflow (`.github/workflows/console-release.yml`, tag `console-vX.Y.Z`). Nothing of it is in the wheel or the sdist.
- **`GET /catalog/{ref}/graph` and `GET /bundles/{bundle_id}/graph`** on the server: a bundle's own graph as JSON, the nodes and edges `aip compile --json` prints, with the source and the files' contents. It is what the console draws a procedure from and shows as its source. `GET /bundles/{bundle_id}` now says the `revision` a bundle is published as (`null` for a draft).
- **Runs are recorded on your own machine with nothing to start** (plan S2). `aip config server local`, which the installer now sets, points the client at a server on this machine that the first command starts when it finds none: `aip run` records the run, `aip runs`, `aip list` and `aip audit` read it back, later commands reuse the same server, and it stops by itself after 15 minutes without a request. The store is one file under the user data directory (`~/.local/share/aip/server/store.rl`), so nothing is lost between starts. It listens on `http://127.0.0.1:8247` (`AIP_LOCAL_PORT`; `AIP_LOCAL_DATA` moves the store, `AIP_LOCAL_IDLE` the wait), and `aip server --local --stop` stops it by hand. A run never fails because the local server could not start: it is reported as not recorded, with why. `aip config server URL --token T` points at a server elsewhere and `aip config server none` at none; `AIP_SERVER` takes the same three values. `--server URL` still works.
- **`aip export runs [name] --since DATE -o audit.rl`** writes the server's runs that match (also `--agent`, `--session`, `--user`, `--draft`, `--published`), and the procedures they ran, as one Relate file: each run's record beside the graph of the bundle it ran. It opens with the engine's own tools, with no server, and every query in `docs/language/queries.md` runs on it.
- **`aip runs --user`, `--draft` and `--published`**, beside `--agent` and `--session`.

### Changed
- **`aip governance` is `aip audit`** (plan S2): the queries review the record and the catalog, and none decides who may do what. The endpoint is `/audit`, the SDK method `Client.audit()`, the module `aip.server.audit`. `aip governance` answers with the new name.
  - **Twelve queries on the 0.9 record.** Beside `confidence-fired`, `failing-aggregations`, `model-answers` and `agent-routes`: `failing-scripts` (the runs that stand failed at a script, with its message), `untaken-branches` (a route's branches, its `Confidence_Below` line included, that no recent run took), `repeated-cycles` (loops that went round more than `--repeats` times, and whether they ended on `Until` or the cap), `missing-fields` (no `Use_When`, `Do_Not_Use_When` or `Avoid`), `empty-results`, `unused-data` (keys and model answers nothing reads), `cycles` (every loop, what bounds it and what it produces again each pass) and `lineage --key K` (what a key is derived from, through a `For` too). `manual-decisions` and `unmeasured-routes` are gone with the agent fallback: no answer is given by hand, and `agent-routes` lists the routes an agent steers.
  - **Filters**: every query takes `--name`, `--agent`, `--session`, `--user`, and `--draft` or `--published`, with `--window` and `--limit`.
  - **Stored queries are back, on both backends**: `aip audit --save NAME --cypher '...'` keeps a query of your own on the server, `aip audit NAME` runs it with the same parameters, `--delete NAME` removes it. Every audit query runs in a transaction that is never committed, and one with a writing clause is refused when it is stored.
- **The server says whether a run is a draft's.** A run of a folder whose bundle the server already holds as a published revision is recorded as a run of that revision (`draft: false`, with the `revision`), not as a draft; a bundle with no revision is a draft whatever the client claimed. `POST /runs` replies with `draft` and `revision`, and the run file takes them.
- **`GET /health`** on the server (`aip`, `language`, `backend`, `local`), with no token.
- The line printed when a run is not recorded now reads `run `aip config server local` to record runs on this machine, or `aip config server URL` for a server elsewhere`.

### Changed
- **The server stores bundles and the record of runs, on Relate or Neo4j** (plan S1; `docs/server-design.md` is rewritten around it).
  - **One store, two backends, one body of Cypher.** `aip server` keeps everything in one graph: by default a single Relate file it alone writes (`~/.local/share/aip/server/store.rl`, `--path` or `backend.path`), needing no database beside it; `--backend neo4j` for a database several people share, Aura included. A published procedure is in the store as the same nodes and edges its `.rl` holds, beside its revisions and its runs. **The filesystem backend is gone**, with its file lock: a config that still says `kind = "filesystem"` or `root` is refused with where the store is now, and procedures are published again with `aip publish`.
  - **Publishing is by bundle.** `aip publish` sends the `.rl`; the server verifies it as `aip run file.rl` would (a file that is not a bundle, was edited, or is of another language version is refused with that error, and nothing is stored), merges it by its id and gives it the next revision under the procedure's name: `billing_support@1`, `@2`, numbered by the server. Publishing a bundle the server already has is a no-op that answers with the revision it has.
  - **Drafts.** A run of a folder or a file with a server configured uploads the bundle with no revision, a draft, so the run can be recorded against exactly what ran. A draft is not in the catalog or in search; publishing it later promotes it. `GET /bundles` lists what the store holds.
  - **`aip pull` and `aip get` receive the bundle itself**: the server hands back the procedure's own subgraph as an `.rl`, which the client verifies against the id it asked for.
  - **Runs are recorded whole, and who ran them.** The client posts the run at every stop and the server keeps it against the bundle it ran (a run of a bundle the server does not hold is refused). The record carries `agent` and `session` as the client gave them and `user`, which the server fills in from the token: the config file's new `[tokens]` table names one token per person. `aip runs` filters by name, status, agent and session; the server also by user and draft.
  - **Everything the record says is in the graph.** Each step run is a node tied to the step of the procedure it ran, with how long it took, the model's share of that, how long the run waited for an agent and who answered, whether a decision went out in a batch, where a route went and whether its confidence check fired and why, why a loop ended, and each answer with its confidence. `docs/language/queries.md` has the queries: a run's path, where its time went, checks that fired, what the model answered and how sure it was, aggregations that fail most, the lineage of a key, who answered the tasks, why loops ended. Each is run in the tests against both backends.
  - **`aip governance` answers four queries on the new store**: `confidence-fired`, `failing-aggregations`, `model-answers` and `agent-routes`, filtered by procedure, agent, session or user. The other 0.8 queries and stored queries are not served yet; they return with the rename to `aip audit`.
  - **Tokens have three scopes**: `read`, `run` (upload a draft, record a run) and `publish`. `--token` grants all, `--read-token` reads only.
  - **Built-in procedures**: a server publishes the bundles shipped inside the package the first time it sees each one, and does not bring one back after it is retired. None ships yet.

### Removed
- **`aip db`** (load, list and export straight into Neo4j with no server) and the `aip.db` module. The server is the store's only writer: loading is `aip publish`, listing is `aip list`, getting a revision's folder back is `aip get --out`, and looking inside a store is the database's own tools with `docs/language/queries.md`.
- The server no longer runs anything: the 0.8 endpoints that stepped a run (`POST /runs/{id}/result`, `/procedures/{ref}/peek|step|answer|capabilities`) and served a skill's files (`/catalog/{ref}/files`) are gone. Every run is local to its client.

### Changed
- **The runtime after its first use** (plan R5, the runtime's half of the answer to the three reports under `docs/language/reviews/`; `docs/cli-json.md` is rewritten around it).
  - **Answers are as strict as inputs, and a refused answer leaves the pause.** `aip resume --answers` is refused as `invalid_output` when it has a key the pause did not ask for (`invalid` names it), more answers than the pause has tasks (`invalid_tasks`), a task left out (`missing_tasks`; `missing` holds key names only), or a field on an answer beside its value. Nothing is applied, the run is still `paused` with the same tasks, and the next `aip resume --answers` answers it. Before, an extra key and a surplus answer were dropped silently, and a task left out failed its pass, after which the run had to be resumed bare before it would take an answer again. Every task of a pause is answered in one `resume`.
  - **The last pass is announced, and a loop at its cap is over.** A task inside a `Loop` with a cap carries `pass_of`, the cap, and `last_pass`, true on the last pass the cap allows, so an agent asked to fix on the last pass knows nothing follows. `loop_cap` is `resumable: false` in both its forms (an `Until` loop out of passes, a list longer than `At_Most`): a retry failed identically, and `aip resume` now says so instead of trying. Its error names the loop as `loop` (`step` is `null`), with `cap` and `count`, and no pass that never ran; the loop's exit entry is written to the history with `exit.reason: cap`.
  - **The runtime's loop keys are not in the state.** `index`, `iterations` and each loop's own key are read by steps as before, but the saved state of a run never holds one; the run file keeps them under `loops` while the run is under way and a run that is over has none.
  - **The record says where the time went and who answered.** Every step's history entry has `seconds`; a `Decide` entry `model_seconds` (the call alone) and, when it went out with other `For` passes in one call, `batched: true` and `batch_size`; a `Task_Agent` entry `answered_by` (`{"agent", "session"}`) and `waited_seconds` (pause to answer); the run `started` and `finished`. The `Until` test at the head of a loop pass is written on the pass's first entry (`until`). One name per thing: the run's cursor is `position` (it was `at`, which is also an entry's timestamp); a read key appears in `input` under the name the step reads it by (`tone`), a route keeping the dotted path as `read`; a route says `to` once, and its `check` has `reason` only when it fired; the bundle id is on the run, not on every entry. The run file's keys are documented in `docs/cli-json.md`, The run file; "history" is the word for a run's entries and "record" for the whole run.
  - **`aip runs` works without a server.** It lists this machine's run files (id, name, status, agent, started, updated; the same filters), and `aip runs <run_id>` prints the run step by step: step, kind, pass, when, `+MS`, and who answered or where it went and why (`--json` for the record). An unknown id answers `no run <id> on this machine`.
  - **`--progress` reports as the run goes and says what happened.** A line is printed the moment its entry is written, inside a batch of `For` passes too, and carries a decision's answers (value and confidence), an aggregation's results, a route's `to` and whether its check fired, who answered a task, a loop exit's `where`, and `seconds`.
  - **A pause says how to answer it**: `hint`, one line with the shape of an answer and that the bare value is enough for a `true_or_false`, `choice` or `score` key.
  - **`aip info`** nests a loop's steps under the loop with its header as written (`Until check_summary.all_hold, At_Most 3, Else_Fail`), prints the whole bundle id, and shows the opening of a description that is a whole prompt.
  - **Smaller**: the line `not recorded: no server is configured` is printed by `aip run`, once for the run, and not by its resumes or by a command that changed nothing; `aip --help` has a line per command; `aip server --help` prints help (it raised an import error); a file that is not a bundle is `<path> is not an .rl bundle` and nothing more.
  - **SDK**: `Task.last_pass` and `pass_of`, `Paused.hint`, `RunError.stopped`, `RunRecord.started`, `finished` and `table()`, `Client.runs()` from the run files when no server is configured; `on_step` is called as each entry is written; `Engine(on_entry=, timer=)`.

### Added
- **`ambiguous_read`**, an error: two reads of one step that end in the same word (`Read review.iterations, revise.iterations`) would reach the step under one name, and one was lost silently. Read the keys whole (`Read review, revise`) and name the field in the script or the template.

### Changed
- **The language after its first use** (`docs/language/spec.md`; plan L6, answering the three reports under `docs/language/reviews/`). What a procedure means changed in four places. `With Confidence_Above p` holds only strictly above `p`: an answer at the bar is barred, in an aggregation and in an `Until`. A `score` answer's `value` is its level's label (`"high"`), not the level's number, and its `probabilities` are keyed by label; routes and conditions already named labels, an agent or a script now answers with one, and the model's number is mapped when the answer arrives (`score`, the expected level, stays a float). Each loop's name is a key the runtime writes, `revise.index` inside the loop's body and `revise.iterations` after it, so a step after nested loops can read the inner loop's count; the bare `index` and `iterations` remain as shorthands for the innermost loop running and the last loop that exited, and a key, loop item or collected list may no longer share a loop's name (`duplicate_name`). An `Until` is tested at the head of every pass, the first included, so a loop whose answer already holds runs no pass: the spec said "the first pass always runs", which was never true of the runtime and which `ticket-triage` depends on not being true. The type alias `noul` for `true_or_false` is gone.
- **The spec is reorganised around what a first reader needed**: a "shape of a card" summary at the top of 2.1 (the three clause orders, what a target may be, `.value` and `.confidence` in a `Read` and why a `Route` refuses them, where the header ends); loops in a section of their own, 2.6 (every form, the caps and `Else_Fail`/`Else_Exit`, `Continue`, `Again` said plainly, `Collect`, the loop keys); one example vocabulary (`classify`, `classification`) throughout; which number each check reads (`Confidence_Below` the answer's `confidence`, a bar the probability of the condition); and section 3 says exactly what `bundle_tampered` verifies (the source, the files and the graph as read back, not the bytes of the `.rl` file, so the bundle id is the artifact's identity and a file checksum is not).
- **One mistake, one error** (`aip compile`). A finding that is only the consequence of another is no longer printed: a misspelt `Next_Step` is one `unknown_step`, not that and an `unreachable_step` for every step behind it (the same for a missing `Next_Step`, a loop without its exit line, and a flow across a loop's braces); a `Decide` without `Produce` is one `missing_clause`, without an `unknown_key` at each reader; `yes -> ...` and `no -> ...` on a `true_or_false` are one `unknown_label` naming both, without a `missing_branch`; a second producer of a key is one `duplicate_producer`, without the `type_mismatch`es after it. A `syntax_error` on a word within an edit or two of a keyword that could stand there says which (`got 'Answer_Quesions'; did you mean Answer_Questions?`), and a header line written below the header says where it belongs (`'Use_When' belongs in the header, before the first step`). The messages for `type_mismatch` and `unavailable_key` read as sentences.
- **`aip fmt` lines up a multi-key `Produce`** as it does a block of questions: continuation lines under the first key, the types under each other, the descriptions under each other. `aip fmt` and `aip fmt --check` take a directory of program directories (`aip fmt --check examples/language`).
- **The examples** are in the formatter's form, and CI fails if they drift (formatting a procedure changes its bundle id). `billing-support` checks `Confidence_Below 0.9`, which the decision model's answers reach: a clearly calm or clearly angry message routes by its value, a mixed one is escalated by the check. `fixed-policy` carries its approved claims in the `policy_claims` question and in `assets/claims.md` for the agent, so a compliant note passes the first check; its `fix` task (and `dynamic-policy`'s) also reads `check_summary`, and the prompt says which number the bar is on. Stale comments are gone.
- **The package version is `0.9.0`**: `aip --version` prints `aip 0.9.0 language 0.9`.

### Added
- **`decide_reads_nothing`**, a warning: a `Decide` with no `Read` has the model judge nothing but its questions.

### Changed
- **One package.** The language's parser, checker, formatter, graph and bundle, the `aip-spec` package through 0.8, are part of `agent-instruction-protocol` as `aip.compiler`; `pip install agent-instruction-protocol` is the whole install and `aip --version` prints one line, `aip <version> language <language version>`. `aip compile`, `aip fmt` and `aip export` are unchanged, including `aip compile --json` for the editor; the `aip-spec` command is gone (it was the same three commands under another name), and a Python import of `aip_spec` becomes `aip.compiler`. The `aip-spec` distribution on PyPI stays at 0.8 with no further release. Why: a 0.9 procedure is a bundle only the runtime can run, so nobody installs the compiler alone; the extension, CI, the SDK and the MCP server all go through `aip`.

### Added
- **Labels on a produced answer, and the agent deciding in a `Task_Agent`** (`docs/language/spec.md` 2.1, 2.4; plan L4). An `Execute`, a `Task_Agent` or a `Start` input declares a `choice` or `score` with its labels, as a question does: `Produce tone: choice [angry, calm] "..."`. The compiler knows them, so a route over such an answer is checked like one over a question (`unknown_label`, `missing_branch`), a `choice` or `score` key without them is `question_labels`, and the formatter writes them back. A `Task_Agent` pause carries `labels`, the values the agent may answer with, beside `answer_with`. The new example `examples/language/billing-support-agent` is `billing-support` with `triage` as a `Task_Agent` producing `billing: true_or_false` and `tone: choice [angry, calm]`, the route on `tone` with no confidence check, the same script and reply: side by side the two show model vs agent, and the agent one runs on a machine with no decision model.
- **Source classes in the bundle** (`docs/language/bundle.md`). A route's `READ_BY` edge carries `source`, the class of the answer it reads as the checker found it: `measured` (a `Decide`), `scripted` (an `Execute`), `agent` (a `Task_Agent`), `input` (`Start`) or `aggregated`, so governance can ask which routes an agent's answer steers.
- **The `aip` command and the SDK on the 0.9 engine** (`aip.client`, `aip.Client`; `docs/cli-json.md`, `docs/sdk.md`). `aip run <target> --inputs JSON` takes a program directory (compiled on the spot), an `.rl` bundle, or a published `name[@rev]`; every run runs on this machine from a cache of bundles (`~/.aip/bundles/<bundle id>.rl`; `aip pull name[@rev]` and `aip pull --all` warm it, and a name runs from it when the server is down), and every stop writes the run file `~/.aip/runs/<run id>.json`, the whole run, so `aip resume <run id> --answers JSON` works from anywhere and reopens the exact bundle the run started on. `--inputs` and `--answers` take JSON inline, `@path` or `-`. When a server is configured (`aip config --server URL`) the run is recorded there at every stop, a folder or file run as a run of a *draft* bundle uploaded first; with none the run works and the command ends with one line on stderr, `not recorded: no server is configured; run aip config --server URL ...`. The printed objects follow the engine: a pause is `{"paused": "task" | "decision", "step", "reason", "tasks": [...]}` with one task per `For` pass waiting at the step, answered by index; done carries `result`; an error carries `pass` and `passes`; `--progress` prints one line per record entry. New flags `--batch N`, `--agent`, `--session` (and `AIP_BATCH`, `AIP_AGENT`, `AIP_SESSION`); the CLI's default agent is `cli`. `aip info <target>` describes a folder, a bundle or a published name (`--json`, `--example-inputs`); `aip publish` takes a folder or an `.rl` and prints `name@revision`; `aip get name[@rev] --out DIR` writes the program directory from the bundle; `aip runs` filters by `--agent` and `--session`; `aip config` gains `--batch`. The SDK: `Client.compile`, `describe`, `run`, `resume`, `search`, `list`, `pull`, `pull_all`, `publish`, `get`, `pin`, `retire`, `runs`, `run_record`, `governance`, each returning a typed value (`Paused` with its `tasks` as `Task`s, `Done`, `Description`, `Pulled`, ...), and the errors `CompileError`, `InvalidBundle`, `NotFound`, `NoServer`, `InvalidInput`, `RunError`, `ServerError`. `aip.client.server` lists every HTTP call the client makes, the contract the server milestone implements; `tests/fake_server.py` is an in-memory server speaking it.
- **Loops, batching, the decision model, batched pauses, the record with passes** (`aip.model`; `docs/language/runtime.md`, Loops, Batching, Pauses, The record). `For` and `Loop` run in every header form: `For ... Over ... As ..., At_Most n, Collect ... Into ...` with independent passes over a copy of the state and the collected list in input order; `Loop ... Until <condition>, At_Most n, Else_Fail | Else_Exit` with the condition tested at the head of every pass and the moment a body step (or a loop in the body) produces the watched answer, ending the loop there; `Loop ... n Times`; the fold `Loop ... Over ... As ...`; `Continue` from a step or a route branch; `Again <step>` re-running the loop's level and ending the pass when the loop is reached; `index` and `iterations` as the runtime's keys. A list longer than the cap, or an `Until` loop at its cap with `Else_Fail`, fails the run with a new error kind, `loop_cap`. `For` passes run in batches (`Engine(batch=)`, `start(batch=)`, default 10): a batch whose body is one `Decide` with the same `Read` keys on every pass is **one model call**, the question keys suffixed with the pass index (`follows__3`) and mapped back so the record shows one entry per pass as if each had called alone; any other body drives the passes together, and the passes waiting at the same step go out as **one pause** with one task per pass, answered by index. A pass's entries are appended when its batch completes, in input order, so the record is identical at every batch size. **`TypeSafeResolver`** (`aip.model.typesafe`) is the decision model: a step's questions become TypeSafe's `Noul`, `Choice` and `Score`, the `Read` keys (and the history when asked) go as the state, and the reply comes back as the answer objects of spec 2.4. Every record entry carries `pass` and `passes` (every enclosing loop's pass number); a loop writes an entry when it exits with `iterations`, the collected list and why it ended; a task in a pause carries the same; the run carries `identity` (`agent`, `session`, `user`), `batch`, and its loop frames, so a run paused inside a loop survives `to_dict`/`from_dict`.
- **The engine runs a bundle** (`aip.model`: `Procedure`, `Engine`, `Run`; `docs/language/runtime.md`). A verified bundle is loaded into an in-memory Relate store (`Procedure.load`) and every step is read from it with Cypher as the run reaches it; the same queries read a server's store. `Engine.start(procedure, inputs)` checks the inputs against `Start` and steps until a pause, the end or a failure; `resume` carries the agent's answers; `retry` runs a failed step again. The state is the spec's (2.3): a step sees its `Read` keys, a dotted read as the one answer under the field's name, every `Produce` key checked for presence and type before it is written, a bare `true` for an answer-typed key stored as `{"value": true}`. The step kinds of a straight procedure: `Decide` through a pluggable resolver (`Resolver.decide(request)` returning one answer object per question, spec 2.4; `ScriptedResolver` ships for tests, `TypeSafeResolver` is the entry above), or handed to the agent with `Agent_Fallback true` when no model is configured or the model fails; `Route` on an answer's value with `Confidence_Below` firing on a low or absent confidence (a `score` branches by the label of its level); `Aggregate` with `All`, `Any`, `None`, `==`, `!=`, `With Confidence_Above` fail-closed, every answer's resolution recorded, each result `{value}` and nothing else; `Execute` launching the script from the cache with `{"state", "assets", "expects"}` on stdin, `Command` honoured, `Requires` checked before the first script, non-zero exit, bad JSON, undeclared keys and the timeout each a failure; `Task_Agent` as a pause with the prompt rendered (`{key}`, `{decision.question.value}`, `{assets[stem]}`), the references and `answer_with`; `End` returning its `Read` keys. A pause is one step with a list of tasks (one, index 0, outside a loop), answered by index. The bundle's files are unpacked once per bundle id under `~/.aip/cache/<id>/`. Every record entry carries the bundle id, the step, its kind, the pass, the time, what it read and what it produced; a decision's who answered, a route's check and branch, an aggregation's resolutions, a script's stdin and seconds. `aip_spec.write_graph` and `read_graph` are the public names of the one body of Cypher that moves a graph into and out of a store.
- **The VS Code extension checks as you type** (`editors/vscode`). The extension that carried the grammar now has a build (`npm run build`, esbuild) and an activation: on open, on every change (debounced, `aip.debounceMs`) and on save it runs `aip compile --check --json --stdin` on the file's folder with the buffer's text and shows every diagnostic as a squiggle at the compiler's line and column, with its code; a status-bar item shows the compiler's version, or "aip not found" with the install hint; `aip.command` names the command (`aip`, a path, or `uv run aip`). `npm test` runs the grammar through vscode-textmate over the examples and the diagnostics against a fixture with one error, with node's own test runner. For it, **`aip compile --stdin`** (and `aip-spec compile --stdin`) takes the source from standard input in place of PATH's `procedure.aip`, reads the folder's other files from disk, and names the file in the diagnostics; `aip_spec.compile_folder(folder, source=...)` is the same in Python.
- **The bundle** (`aip compile <folder> [-o FILE]`, `aip export <bundle.rl> --out DIR`; `aip-spec` has the same commands; `aip_spec.compile_folder`, `write_bundle`, `read_bundle`, `export_bundle`). A compiled program is one file, `<name>.rl`, a Relate single-file graph database holding the source of `procedure.aip` byte for byte, every file under `assets/`, `references/` and `scripts/` with its bytes, mode and sha256, and the graph derived from them: the procedure, the steps by kind, the loops, the state's keys, the questions, the aggregations and the files as nodes; the flow (`NEXT`, `CONTINUES`, `AGAIN`, a route's `BRANCH` and `BELOW`), the state (`PRODUCES`, `READS` with the field and whether it is an interpolation), the loop structure (`CONTAINS`, `ENTERS`, `OVER`, `BINDS`, `COLLECTS`, `WATCHES`) and the files a step runs, is prompted by or uses as edges. `docs/language/bundle.md` is the schema. The bundle id is the sha256 of the source and every file's hash, so an unchanged program compiles to the same id anywhere. `aip export` writes the program directory back, byte for byte; before a bundle is exported it is verified (hashes, id, and the stored source compiles to the stored graph), and a bundle edited by hand in Cypher is refused as `bundle_tampered`. `aip compile --json` adds `bundle_id` and `graph`, the same nodes and edges with their source spans and without the file contents, for the editor. Writing or reading a bundle needs Relate installed, which `scripts/install-relate.sh` does from its GitHub release (it is not on PyPI yet); `--check` and `fmt` never need it, and `aip` prints the install hint when a bundle is asked for without it. `scripts/fresh-venv.sh` proves a fresh environment installs both packages and compiles, exports and recompiles an example to the same id; CI runs it when it has a token for the release.
- **The language's checker** (`aip_spec.check`, `aip_spec.check_path`; `aip compile <folder> [--check] [--json]` and `aip-spec compile`). Every rule in the spec's sections 2.2 to 2.5, reported against source lines in one shape, `{code, severity, message, file, line, column, end_line, end_column, step}`: the procedure's shape (one `Start`, one `End`, names, the clauses each kind needs, question labels), the flow (every target exists and is reached, a loop body is entered and left only through the loop's own lines, no cycle outside a loop body, `Again` only in a `Loop` and only to a step the loop is reached from), the loops (a cap on every one, an exit line, `Until` on an answer the loop can see, `Collect` of a key every pass produces), the state (every `Read` and `{interpolation}` available on every path, one producer per path with rebinding inside loop bodies, types agreeing, a `For` body's keys per-pass unless collected, a `Loop` leaving what every exit wrote), routes and conditions (one answer, every value named, labels and levels checked, `comparison_required` on a `choice` or `score`, `confidence_on_aggregate`, the source classes with `confidence_on_unmeasured_source` and `unmeasured_route` as warnings, aggregation sources through collected lists), and the files on disk. `--json` prints the diagnostics for the editor; the exit code is 1 on any error, 0 with warnings. The spec's section 2.2 lists every code; `aip_spec.CODES` is the same table. The bundle itself arrives with the next milestone, so `compile` writes nothing yet and says so.
- **The language's parser and formatter** (`aip_spec.parse`, `aip_spec.format_program`; `aip fmt <path>...` and `aip-spec fmt`, with `--check`). A hand-written parser for the grammar in the spec's section 2.1 and glossary: every step kind, `For` and `Loop` in every header form, `Answer_Questions`, `Aggregations` with the condition grammar, `Confidence_Below` routes, named strings, triple-quoted strings, `{key}` interpolation, comments. Keywords match in any case and every glossary alias is accepted (`Task` for `Task_Agent`, `Next` for `Next_Step`, `w/ Conf` for `With Confidence_Above`); the formatter writes the canonical spelling, two-space indent, one clause per line, and keeps every comment. Every node carries its line and column; a syntax error names the line, the column and what was expected. `aip --version` prints `aip <version> language 0.9`.

### Changed
- **The decision model is an endpoint, not a vendor; there is no fallback** (`aip config`, `aip.model.typesafe`; `docs/cli-json.md`, `docs/sdk.md`, `docs/language/runtime.md`; plan R4). `aip config --decision-model URL --decision-model-key KEY` configures the model this machine decides with: any endpoint with the TypeSafe API shape (questions in, answer objects with their confidence and probabilities out), reached through `typesafe-sdk` with its `base_url`; the URL defaults to TypeSafe's, and `AIP_DECISION_MODEL` and `AIP_DECISION_MODEL_KEY` override the file (`decision_model: {url, api_key}`). `TYPESAFE_API_KEY` is no longer read. `aip config` prints the endpoint and whether a key is set, never the key. A `Decide` with no model configured fails the run with `no_decision_model` and the configuration hint; a model that fails (unreachable, a refused key, a bad reply) fails it with `decision_model_failed` carrying `model`, `endpoint` and `cause`; `aip resume <run_id>` retries the step either way. The decision pause is gone from the engine, the CLI's JSON, the SDK (`Paused.kind` is only `task`; `Paused.reason` and `Task.questions` are removed) and the docs, with `Procedure.given_by_hand`, `answers.by_hand` and a route's `reason: hand`. The record's `answered_by` is `{"model": <the reply's model>, "endpoint": <url>}`. Answers from agents and scripts are checked where they are produced: a `Task_Agent`'s answer is a bare value or `{"value": ...}` among the key's labels and anything else on it is `invalid_output` (the pause stands); an `Execute`'s answer may carry `confidence` and `probabilities` (and `noul` or `score`) as a model's would, so a route's `Confidence_Below` on a script's answer reads a real number, fires as `absent` when the script wrote none, and a stray field or a label the key does not declare is `invalid_output` at the script, not `no_branch` at the route; a `Start` input under labels is checked the same way.
- **Decisions need a model; `Agent_Fallback` is gone** (`docs/language/spec.md`, decisions table "Decisions need a model (2026-11-09)"; plan L4). A `Decide` is always answered by a decision model, so every decision answer carries its confidence and a route's `Confidence_Below` on one always means something; with no model configured the run fails at the decision (`no_decision_model`, resumable once one is set) and there is no answering it by hand. What an agent decides, it decides in a `Task_Agent`, producing an answer under declared labels. `Confidence_Below` and `With Confidence_Above` are allowed on a decision's or a script's answer and are errors elsewhere: `confidence_on_agent_answer`, `confidence_on_input` (new) and `confidence_on_aggregate`; the warnings `confidence_on_unmeasured_source` and `unmeasured_route` are gone, since routing on an agent's answer with no check is the intended way to decide without a model. `examples/language/billing-support` drops `Agent_Fallback true` and needs a model. The `decision` pause and `reason: hand` no longer occur (`docs/cli-json.md` documents the `task` pause of `billing-support-agent` in their place); the engine's unreachable fallback path goes with R4.
- **The bundle's graph names data as the 0.8 graph did** (`docs/language/bundle.md`, Zach's review 2026-11-09): the `Key` node is `Data` (id `data:<name>`), `HAS_KEY` is `SUPPLIES`, and `READS` is reversed and renamed `READ_BY`, so a data-flow path reads left to right, `(Step)-[:PRODUCES]->(Data)-[:READ_BY]->(Step)`. `aip compile --json`, the engine's queries and the bundle id's inputs are unchanged apart from the names (the id never covered the graph).
- **The spec, where the checker found it silent** (2.1, Flow and Loops; 6, Reserved names): a pass starts at the first step written in a loop body; a loop's exit line is required, and `Continue` as an exit is only for a nested loop; a body is closed to `Next_Step` in either direction; every loop has a cap; `Again` is for `Loop` passes and ends the pass when the loop is reached; `index` and `iterations` are reserved; an aggregation's source may be a list collected from an answer key (the table had said "a `boolean` key", which 2.2 forbids). `examples/language/ticket-triage` and the spec's summary example end the review loop with `Continue` and the batch loop with `Next_Step summarize`, and the example gains `Requires python 3.10` and the two stub scripts it names.

### Removed
- From `aip-spec`: the pydantic models of the YAML format, the JSON Schema, the runtime block and the commands `validate`, `schema`, `runtime`, `skill`, `example` and `upgrade`. The package now depends on nothing.
- From `aip`: the 0.8 engine (`aip.model.steps`' `Decision`, `Router`, `ClientTask`, `Execution`, the cursor-based loop, the `<question>_confidence` keys, the `manual` attribution) and `aip.spec`, which built it from a skill folder; `aip.model` is the 0.9 engine above. The 0.8 server still sits on the old names until S1 replaces it.
- From the `aip` command: `validate`, `upgrade`, `schema`, `runtime` and `skill` (the YAML format's tooling; the 0.9 skill and `aip skill install` return with K1); `run --input FILE` (now `--inputs JSON`, inline or `@FILE`), `resume --input` (now `--answers`), `--interactive` (an agent answers pauses from the JSON), `--run-file`; the run on the server (`aip run <name>` ran on the server in 0.8; every run is local now and recorded). From the SDK: `Client("./folder")` (targets are per call), `validate`, `info` (now `describe`), `Driver`, the 0.8 `Paused` fields (`state`, `questions`, `confidence`, `fallback`, `task`, `answer_with` moved onto each `Task`). The 0.8 client modules `backend.py`, `executor.py`, `resolver.py` and `runner.py` are gone; the engine runs scripts and asks the model.

## [0.8.0] — 2026-11-03

Format `0.8`, the first format change since `0.6a1`, and it is breaking: a skill written for `0.6a1` no longer loads, and `aip upgrade <folder>` rewrites it. Four changes to the format, bundled because each rewrites part of the validator's state checker and each changes the runtime block every `SKILL.md` carries: the start step is an explicit `start` step that holds the procedure's inputs; a key may have several producers, so a later step may overwrite one; decision `thresholds` and the `review` pause are gone, replaced by confidence keys a decision writes into the state and a check a router applies to them; and the validator classifies what feeds each router as deterministic, measured or unmeasured, which the server records so governance can report the runs that passed through an unmeasured route. The plan was [#18](https://github.com/zach-blumenfeld/aip/issues/18). `aip --version` prints `aip 0.8.0 format 0.8`.

### Added
- **The `start` step.** A step of `kind: start` holds the procedure's `inputs` (what the client supplies) and names the first runnable step in `inputs_to`. Exactly one, in any position (`missing_start_step`, `multiple_start_steps`), nothing hands off to it (`edge_into_start`), it is not runnable and has no outputs. Before, the start was `steps[0]`, which had to be runnable and whose `inputs` doubled as the procedure's; that special case sat in the validator, the loader, the engine, the records, the Neo4j projection and the console. `steps` now needs three entries at least. The engine runs the start step as a pass-through: it checks the start input against the declared types and writes the first history entry (`"kind": "start"`); it has no `--progress` line. `aip info` and `describe` report the start step and its inputs; `procedure.start` in a published record is its name; the Neo4j projection labels it `Start` and `STARTS_AT` points at it.
- **Confidence keys and the router's check.** A decision may list question names under `confidence`; for each, a decision model's answer also writes `<question>_confidence` into the state, a `float` in `[0, 1]`: the probability the model put on the answer it gave, TypeSafe's own confidence for a `choice` or `score` and `|2p - 1|` for a `noul`. It is the same number the history's attribution records (`confidence` per question), and a declared output, so the data-flow rules apply to it like any key (`unknown_confidence_question` when the list names a question the step does not ask). A router may carry one check, `confidence: {key, below, to}`, applied before the value match: when the key is below the bound, or absent, or null, the run goes to `to`. Unknown confidence is low confidence; nobody invents a number. The check guards a model's answer: when the branch key's latest producer in the run's history is a decision answered by hand (`resolver: manual`), the check is skipped and the hand answer takes its branch, since the client stands behind it and there is no number to read (`Procedure.resolve` takes the history; `POST /procedures/<ref>/peek` accepts it). The router's history entry records `"confidence": {"fired", "reason": "low" | "absent" | "null"}` beside `to`, or `{"fired": false, "reason": "manual"}` for a skipped check, and the `--progress` line is unchanged. One check per router; a router that needs more is two routers. The key must be a `float` declared on some path to the router (rule 1 on declaration, not on presence at runtime); `branch_on` must be `boolean`, `string` or `integer` (`unbranchable_type`).
- **`fallback` on a decision, default `false`.** Whether the client may answer the questions by hand when it has no decision model. With `false` a run with no model stops at the decision with a new resumable error, `no_decision_model`, naming the step and the field in both backends before anything is posted, and an answer by hand on `resume` is refused the same way (`fallback_not_allowed` from the engine); once a key is configured a bare `aip resume <run_id>` asks the model. With `true` the decision pauses for the agent as before, the manual attribution carries no confidence, and the step writes no confidence key; a router downstream does not check one for it and takes the branch the agent chose (`reason: manual`). `aip config` says what happens without a model. The decision pause carries `confidence` (the list) and `fallback` instead of `thresholds`.
- **Routing sources, classified.** For each router the validator classifies every producer of its `branch_on` key that can reach it: deterministic (a start input, or a script's output when the router checks no confidence the script declares), measured (a decision with `fallback: false` whose `confidence` list names the branch question and whose `<question>_confidence` the router checks; or a script or client task whose outputs include the number the router checks), or unmeasured (a decision with `fallback: true`, a decision whose confidence is not emitted or not checked, or a client-task output the router does not check); with several producers the worst wins. Three findings follow: `confidence_on_unmeasured_source` (warning: a check guards a model's number and the source gives none, so a hand answer bypasses it and only the runs a model answered are measured), `unmeasured_route` (warning: a probabilistic choice routed the run and nothing recorded how sure it was) and `declared_confidence` (info: a router checks a confidence a script or client task declared itself, legitimate for calibrated code, discouraged for an agent). Deterministic sources report nothing. `aip_spec.classify_sources` returns the class per router and `validate_skill` carries it as `routers`.
- **`info`, a third severity.** The validator's issues are `error`, `warning` or `info`; info never fails validation. `aip-spec validate` and `aip validate` count infos beside warnings; `POST /catalog` returns `infos` beside `warnings`; `aip.Validation` gains `infos`. The one info today besides `declared_confidence` is `duplicate_producer`, below.
- **`aip upgrade <folder>`** (`aip-spec upgrade`, the same command; `aip_spec.upgrade`). For a skill in any recognised earlier format it replaces the runtime block, inserts a `start` step before the old first step carrying its `inputs` and pointing at it (the old step keeps its inputs, now consumed), drops every `thresholds` block, sets `fallback: true` on every decision (a run in those formats could always be answered by hand, and the upgrade keeps that behaviour and says so), and sets `metadata.aip-version` to `"0.8"`. The rewrite is line edits, so comments and layout survive; it is checked against the same change made on the parsed procedure and refused (exit 2, nothing written) on a layout the edits cannot follow. It prints each change and what it left by hand (a `confidence` list and a router check where the skill relied on review; `fallback: false` where a decision model is required; for a `0.5a1` skill, the outputs and `requires`), writes the skill and validates it: exit 0 when valid, 1 when the validator still names something. `--check` reports and writes nothing. The validator's `runtime_block_outdated` message names it for `0.5a1`, `0.6a0` and `0.6a1`.
- **Two governance queries.** `confidence-fired` lists, per name, router and reason, how often a check fired in the window and in which runs. `unmeasured-routes` lists the routers the validator flagged (`unmeasured_route`, `confidence_on_unmeasured_source`) on each name's resolved revision, with the source class and the windowed runs of that revision that passed through them. Both backends answer both.
- **The server keeps what the validator found.** A published revision's record carries, per question, whether the decision emits its confidence (`confidence: bool`, where `threshold` was); per decision, `fallback` and its `confidence` list; per router, `source_class` and its `check` (`key`, `below`, `to`); and an `issues` list with every warning and info, each named to its step. `info` returns `issues`. In Neo4j: `Question.confidence`, `Decision.fallback`, `Router.source_class`, `Router.check_*`, a `BELOW {key, below}` edge from a router with a check to where it sends the run (so `NEXT|THEN|BELOW*` walks the whole procedure, and `cycles` names a check in `taken_when` as `key < bound`), `Issue` nodes on `HAS_ISSUE`, `AT` their step, and a decision's `<question>_confidence` projected as a produced `Data` node the router's check `FEEDS` on. A router's `StepRun` carries `confidence_fired` and `confidence_reason`; `Answer` carries `confidence`.

### Changed
- **Keys may be overwritten.** The one-producer rule (0.6a0's rule 2: each key has exactly one producer and is never a start input) is gone. Keys accumulate and a later step may overwrite one, which the runtime always did; the validator now says so as `duplicate_producer`, severity `info`, naming every producer, and a start input may be overwritten. Rule 4 is generalised: every declaration of a key (the start's, every producer's, every consumer's, a question's collapsed type, a confidence key) agrees on its type, the first in step order being the reference (`type_mismatch` names both). The Neo4j data flow allows several `PRODUCES` per `Data` node and no longer feeds the start step its own inputs; `empty-results`, `unused-data` and `cycles` follow.
- **Decisions are answered outright; the `review` pause is gone.** The client's resolver answers every decision with the model and posts the answers with their attribution; nothing pauses for a second look, and `proposed_answers`, `review`, the runner's review prompt, `reviewed()` and the attribution's `reviewed` and `proposed` fields go with it. What a threshold used to trigger, a router now decides: check `<question>_confidence` and send a low or absent one where the author wants it. `aip.Paused` trades `proposed_answers` and `review` for `confidence` and `fallback`; `describe_skill` prints `(fallback)` on a decision, `(confidence)` on the questions it names, and a router's check where it printed `(threshold x)`. The `overridden-decisions` governance query is gone (`confidence-fired` is its replacement); `Answer` loses `accepted`, `reviewed` and `overridden`. The console's review form and threshold editor go in its own `0.8.0`.
- **The runtime block** (`aip-spec runtime`, heading `# AIP runtime — format 0.8`) says the start step holds the inputs, that keys accumulate and a later step may overwrite one, how a decision writes its confidence keys and a router checks one (absent counts as low; an answer the agent gave by its own judgment is not checked and takes its branch), and that an agent may answer by its own judgment only where the step sets `fallback: true`. The `0.6a1` block is kept as `runtime-0.6a1.md`; `LEGACY_VERSIONS` gains `0.6a1`, `ACCEPTED_VERSIONS` is empty (nothing older loads unchanged), `SPEC_URL` and `SCHEMA_ID` point into this repository at the `vX.Y.0` tag that introduces a format.
- **The shipped skills.** `examples/billing-support` has a `start` step, `confidence: [tone]` on `triage`, and `by-tone` checks `tone_confidence` (below 0.6, or absent, goes to `escalate`); `fallback: true` stays, with a comment that the quickstart keeps it on so the walkthrough runs without a TypeSafe key and a production skill turns it off. So the example validates with one `confidence_on_unmeasured_source` warning; a run answered by hand takes the tone the agent gave, and a model's unsure `calm` is escalated. The `aip-compile` skill's embedded example is the same skill; its "When Writing Decisions" says `confidence` and `fallback`, a "Routing on a Probability" section gives the check, the three source classes and when each finding fires, "Declare What Each Step Adds" is two rules plus the info, and the validation checklist names the start-step rules. The `aip-runtime` skill describes the start step, drops the `review` row, and explains `fallback` and the `no_decision_model` stop. The docs follow: `docs/state.md` (the "no deliberate re-computation" gap is closed), `docs/running.md`, `docs/run-modes.md`, `docs/client-execution.md`, `docs/sdk.md`, `docs/cli-json.md`, the specification, and `docs/upgrading.md` opens with the `0.6a1` to `0.8` step.
- **Versions.** Both packages are `0.8.0`; the runtime pins `aip-spec==0.8.0`; `install.sh` installs `0.8.0` by default.

### Removed
- `thresholds` on a decision, `thresholds_of`, `flag`, `threshold` and the default margins in the engine; the `review` pause and `proposed_answers` everywhere; `reviewed` and `proposed` in a decision's attribution; `unknown_threshold_question` (now `unknown_confidence_question`); `invalid_start_step` (the start-step rules replace it); the `overridden-decisions` governance query; `Question.threshold` and `Answer.accepted|reviewed|overridden` in Neo4j. Format `0.6a1` skills no longer load; `aip upgrade` moves them.

### Fixed
- **The filesystem backend starts on native Windows** ([#24](https://github.com/zach-blumenfeld/aip/issues/24)). It imported the Unix-only `fcntl` module at load, so `aip server --backend filesystem` died with `ModuleNotFoundError` before listening. The catalog and run-file locks now go through `aip.server.backends.filelock`: `fcntl.flock` on POSIX, `msvcrt.locking` on Windows, the same exclusive, blocking lock on both.
- **Skill files are read and written as UTF-8 on every platform.** The validator read `SKILL.md` with the platform default encoding, which on Windows is the ANSI code page, so the em dash in the runtime block heading was mangled and every skill failed with `missing_runtime_block`. Every text read or write of a skill file, the runtime block, a run input or the server's config files now names UTF-8.
- **Reference URIs use forward slashes on every platform.** A client-task pause on Windows said `billing-support\references\help.md` where the API promises `billing-support/references/help.md`; the shared form is now always POSIX, as record and script paths already were. The tests run on Linux and native Windows in CI (`.github/workflows/tests.yml`).

## [0.6a1] — 2026-10-19 (aip)

The pin on `aip-spec` moves to its `v0.6a1` release: format `0.6a1` is `0.6a0` plus the `type_mismatch` validator rule (a consumed key carries its producer's type), and a `0.6a0` skill still validates with one warning (`docs/upgrading.md`). `install.sh` installs the `v0.6a1` tags of both repos by default, and `aip --version` prints `aip 0.6a1 format 0.6a1`. The rest of this release is the Neo4j work below.

### Added
- **Four structural governance queries (Neo4j only).** `GET /governance` grows `empty-results` (end steps that read only start inputs, so the result the caller gets holds nothing a step produced), `unused-data` (keys a step produces or a decision answers that no step reads and the result does not return), `cycles` (each control-flow cycle with the router value that continues it and the keys its steps re-produce every time round), and `repeated-cycles` (runs in the window that went round a cycle more than `repeats` times, a new query parameter, default 1, also on `aip governance --repeats` and `Client.governance(repeats=)`). They read the control flow and the data flow as one graph, which is why the filesystem backend declines them with 501 as it does `untaken-branches`; the console lists and renders them with no change.

- **Stored governance queries (Neo4j only).** `PUT /governance/{name}` with `{description, cypher}` keeps a query of your own in the graph (`GovernanceQuery` nodes); `GET /governance` lists it after the built-ins with `builtin: false`, `GET /governance/{name}` runs it with the same parameters the built-ins get (`$name`, `$window`, `$limit`, `$repeats`, `$ids`), and `DELETE /governance/{name}` removes it. The name is kebab-case and not a built-in, the Cypher is EXPLAINed before it is kept (422 `invalid_query` otherwise), and a stored query runs in a read-only transaction with a 30 s timeout that the database enforces, so it can read everything and write nothing (422 `query_failed` when it tries, times out, or raises). Rows come back as the Cypher shapes them, with temporal values as ISO strings. The filesystem backend answers 501: it has no query language to keep one in. `GovernanceBackend` gains `queries`, `store` and `remove`.

### Changed
- **The Neo4j projection carries the data flow.** `Input` nodes on `DECLARES_INPUT` edges (one per step and key, a declaration, not a value) are replaced by one `Data {name, type, description}` node per key per revision, which is what the 0.6a0 state contract allows: each key has exactly one producer and is never overwritten. `(:Step)-[:PRODUCES]->(:Data)-[:FEEDS]->(:Step)` is one hop of lineage, so a variable-length `PRODUCES|FEEDS` path follows a value from the client's start input (`(:Procedure)-[:SUPPLIES]->(:Data)`) to the end step; a decision produces its question names, and each `Question` also `YIELDS` the `Data` its answer lands under. The `requires` block is now on the `Procedure` node (`interpreter`, `interpreter_version`, `packages`, `tools`). The control-flow edges are renamed so no edge name talks about data: `INPUTS_TO` is `NEXT`, a router's `BRANCH {value}` is `THEN {value}`, and the step-run chain of a run, which was also `NEXT`, is `FOLLOWED_BY`, so the procedure's edges and a run's trace through them are told apart by name. Revisions and runs recorded before this keep the old edges; republishing a revision projects it anew. The console is unaffected: it draws the data flow from the catalog API's `inputs` and `outputs` rows.

Before the first script runs, `Execution` checks the procedure's `requires` against the machine (`aip.model.environment`: the interpreter's version and each package's installed version are read from the interpreter that runs `python` scripts, other programs from PATH and `--version`) and fails the step with `requires_unmet`, whose `missing` names every absent item; the run waits before the step, so `aip resume` retries once they are installed. A passing check is remembered for the life of the loaded procedure. `command` launches the script from its folder, with a leading `python` meaning the scripts' interpreter; omitted, it is `python <script>`. `docs/cli-json.md` documents the `requires_unmet` object.
- **Format `0.6a0`, A3: three outcomes, one JSON object each.** The pin on `aip-spec` moves to `v0.6a0-dev3`, whose runtime block says each step sees only its declared inputs. `aip run` and `aip resume` print exactly one JSON object on stdout, documented in `docs/cli-json.md` and tested against the CLI: paused (exit 0, was 3), done (exit 0), or error (exit 1). Every pause carries `state`, the paused step's declared inputs only, with `run_id` and `run_file`; a client task adds `task`, `references`, `answer_with` (was `expects`); a decision adds `questions`; a review adds `proposed_answers` and `review`. `suggested`, the `resume` command string, and the framing paragraph prepended to client-task templates are gone (the model's `SYSTEM_FRAMING` and `include_framing` with it; the format's `framing` flag is ignored). Done is `done`, `run_id`, `state`; the run file then holds the whole history. An error has `error` (`script_failed`, `timeout`, `invalid_input`, `invalid_output`, `requires_unmet`, `server`), `step`, `message`, `run_id`, `resumable`, and per kind `script`/`exit_code`/`stderr`, `seconds`, or `missing`/`invalid` key lists; tracebacks only under `--debug`. A step that fails while running leaves the run file at the state before it and `aip resume <run-file>` with no input retries it; a bad answer leaves the pause in place. `--progress` prints one line per completed step (`to` for routers, `resolver` for decisions, `seconds` for scripts, which the history now records). The model raises `ScriptFailed` and `ScriptTimeout` (both `StepError`, with `InputValidationError` and `OutputValidationError`), the server answers with those kinds and their detail and records them on the run, and the run's recorded pause is the client's. The `aip-runtime` skill is rewritten for these shapes.
- **Format `0.6a0`, A2: each step sees only its declared inputs.** The pin on `aip-spec` moves to `v0.6a0-dev2`. `BaseStep.accept` projects the posted state to the step's `inputs` before anything sees it, and the history records that projection as the step's input. Scripts get `{"state": <declared keys>, "assets", "expects"}` on stdin (`currentState` carries the same object for one version); decisions send `{"state": <declared keys>}` to the decision model, with `history` only when the step sets `history: true`; client-task templates render from the declared inputs. A step's result is checked against its declared `outputs` (`OutputValidationError`: a missing or mistyped key, or for scripts an undeclared one, fails the step naming the key) and merged into the full state; manual decision answers are checked against the question types and labels; `Procedure.run` checks the state holds the outputs of the step the client just answered. The client-task pause's `expects` is the step's `outputs` (it was the next step's inputs), and the done state is the state projected to the end step's `inputs`. The `aip-runtime` skill's `aip-version` is `0.6a0`.
- Format `0.5a1`: the pin on `aip-spec` moves to `v0.5a1`, whose runtime block addresses the executing agent and no longer names `aip run`; the `aip-runtime` skill's `aip-version` follows. A `0.5a0` skill no longer validates.
- Filesystem backend search is now weighted BM25 with Porter stemming (`aip.server.search`, no dependencies) instead of exact-token overlap, so "charged twice" and "refunds" find `billing-support`; the field weights and the exact-name boost are unchanged, and the Neo4j backend's full-text index now uses Lucene's `english` analyzer so both backends stem alike; `ensure_schema` drops and recreates an index that exists with any other analyzer, so an existing database migrates on the server's next start.
- AIP format version bumped `0.4a0` → `0.5a0` (M4; `0.4a0` skills still validate, with a warning) → `0.5a1`.

Upgrading one takes three edits: declare `outputs` on each `execution` and `client_task` step, add a `requires` block when the skill has scripts, and replace the runtime block with `aip-spec runtime` (setting `metadata.aip-version` to `"0.6a0"`). The validator's `runtime_block_outdated` message for a `0.5a1` skill says exactly that, ahead of the `missing_outputs` and `missing_requires` errors that name the steps; the `aip` repo's `docs/upgrading.md` walks through `billing-support` as the example.

- **Format `0.6a0` (breaking): declared outputs and the one-producer rule.** `execution` and `client_task` steps declare `outputs` (name, type, description, like `inputs`); a decision's outputs are its question names; routers and the end step add nothing, and the end step's `inputs` are the procedure's result. The validator adds three rules: every consumed key is produced on every path to its consumer or declared on the start step (`unproduced_input`); each key has exactly one producer and is never a start input (`duplicate_producer`); every `client_task` declares `outputs` (`missing_outputs`). The runtime block says the state only grows. `0.5a1` skills are recognised and rejected with `runtime_block_outdated` (now an error); `0.4a0` is no longer recognised. The `billing-support` example declares `escalate -> ticket_id, queue` and `reply -> reply`, and its script no longer echoes `message`.
- Decision steps take `history` (default `false`): when set, the run's history goes to the decision model alongside the declared inputs. An execution script's stdin is described as `{state, assets, expects}` with `state` holding only the declared inputs; `billing-support`'s script reads `state`.
- The `0.6a0` runtime block says each step sees only its declared inputs: a script's stdin is `{"state": <the step's inputs>, ...}`, a decision is answered from the step's inputs (and the run so far only with `history: true`), a client-task template renders from the step's inputs, and a failing script stops the run to be reported, not done by hand.
- **`requires` and `command`.** A procedure with `execution` steps must declare `requires`: `interpreter` (`name`, optional minimum `version`), `packages` (pip names, optionally `name>=version`), and `tools` (executables on PATH); without it the validator reports `missing_requires`. An execution step may set `command`, the argument list that launches its script from the script's folder (default `python <script>`); its first item must be the interpreter or a declared tool (`undeclared_launcher`). The runtime block tells the agent to check `requires` before the first script and to honour `command`. `billing-support` requires python 3.10.

## [0.5a1] — 2026-10-06 (aip-spec)

The first tagged release of the spec as its own repo. It carries the `0.4a0` and `0.5a0` format work below, which were cut in the `aip` repo without a release section.

### Added
- **`aip-spec`, the format as its own distribution.** The spec moved out of the `aip` repo into this one: the pydantic models, the validator, the runtime block, the `aip` authoring skill, and the `billing-support` example. The package is `aip_spec`, its version is the format version, and it needs only pydantic and pyyaml; `aip` now depends on it. `SPEC_URL` and the schema `$id` point at this repo.
- The `aip-spec` CLI: `validate <folder>` (the output contract below), `schema [--write PATH]`, `runtime`, `skill install [agent] [--path DIR]` / `skill list` / `skill remove`, `example <name> --out DIR`, and `--version`. `scripts/validate.py` is gone: the CLI is the one validator, and the installer puts it on PATH. `aip_spec.skill_dir()` and `aip_spec.example_dir(name)` return the authoring skill and an example as bundled in the wheel (hatchling `force-include` of the repo-root files), falling back to the checkout.
- `install.sh`: installs uv if missing, `uv tool install`s this package at its tag, and runs `aip-spec skill install`, non-fatal when no agent is detected. Agent detection (`aip_spec.agents`) covers Claude Code, Cursor, Windsurf, Copilot, Gemini CLI, Cline, Codex, Pi, OpenCode, and Junie, and is shared with `aip skill install`.
- `SKILL.md`: the validator line is `aip-spec validate ./<skill-name>`; the functional-test step runs the skill with the `aip-runtime` skill when installed and otherwise by executing the procedure per the runtime block, naming no `aip` command; `compatibility` names `uv`.

### Changed
- **Format `0.5a1`: the runtime block addresses the executing agent, not an AIP client.** The "Running" section (`aip run`, `aip search`, the pause and resume loop) is gone, and the Client and Server roles collapse into "You": the agent supplies each step's input, runs its script, answers its questions, performs its task, follows its router, and has the final say. A skill compiled to the spec stands on its own as a structure any agent can execute; the client-side story lives in the `aip-runtime` skill shipped with the `aip` package. The authoring skill's guidance says "the agent" or "free-form reasoning" where it said "the client", and names no `aip` command outside the validator lines and the functional-test step. `0.5a0` skills do not get a legacy entry: their block no longer validates.
- **One format, defined in code (`0.4a0`).** AIP no longer has schema families. The procedure format is defined by pydantic models in `src/aip_spec/models.py`; `assets/procedure.schema.json` is generated from them (`aip-spec schema`) and kept in sync by a test. Steps are typed by `kind`: `decision` (SystemOne questions with per-question review `thresholds`), `execution` (a script under `scripts/` with eager `assets`), `client_task` (a template under `assets/` with lazy `references`), `router` (server-side branching on a client-chosen value via `branch_on` and `branches`), and `end` (the final state shape). The first step is the start; edges are `inputs_to` by step name. Every runnable step declares `inputs` in the AIP type vocabulary, which the server enforces at runtime. Dropped `depends_on`, `parallel`, `one_of`, per-step `outputs`, and the top-level `scope_and_approval`, `modes`, `search_shortcuts`, `integrations`, and `scenarios`. Carried over: `purpose`, `trigger_when`, `do_not_use_when`, `steps`, `anti_patterns`.
- **Frontmatter** collapses `metadata.aip.spec` and `metadata.aip.schemaId` into one string key, `metadata.aip-version`, making `metadata` a plain string→string map per the Agent Skills spec.
- **`source/`** stays required for the material the skill was compiled from; it no longer bundles a schema copy.
- **Portable semantics.** The body begins with the AIP runtime block, verbatim: what AIP is, the client and server roles, the state, and what each step kind does at run time. Every skill carries it so an agent can run the skill with no aip tooling present; it loads with the body, not on demand. The canonical text ships in the package, `aip-spec runtime` prints it, and the validator rejects a missing or edited block.
- **Validation** moved into the package and is exposed as `aip-spec validate`. Graph checks run after the models accept the body: unique step names, runnable start, exactly one end, every edge resolves, every step reachable from the start and able to reach the end, unique input names, thresholds name real questions, and every referenced asset, reference, and script exists on disk. Routers branch on collapsed answers of any type: `true`/`false` for a noul, the label for a choice, the level number for a score, matched against the YAML's string keys; the validator checks a router fed by a decision only branches on values that question can produce (`unknown_branch_value`).
- Format `0.5a0`: the runtime block's Running paragraph gains one sentence for the server case; skills still carrying the `0.4a0` block or `metadata.aip-version: "0.4a0"` validate with a single `runtime_block_outdated` warning. AIP format version bumped `0.3a3` → `0.4a0` → `0.5a0`.
- `examples/billing-support`: a complete procedure skill exercising every step kind. It is the validator fixture here and runs end to end through the loader and runtime in the `aip` repo's tests.

### Removed
- `assets/base.schema.json`, `assets/aip-schemas/`, `scripts/validate_schema.py`, and the schema-family conventions (`$id` matching, bundled schema in `source/`, `aip.tag`). With one format there is nothing for them to check.
