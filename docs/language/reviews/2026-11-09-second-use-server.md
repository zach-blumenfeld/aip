## Findings, ranked by how much they would confuse a new user

1. **A run paused inside a `For` shows none of the work it did.** After step 15's run had classified three tickets, routed them, escalated one, taken two drafts and failed a check, `aip runs 439478c79a714d6e` printed:

   ```text
   run 439478c79a714d6e  ticket_triage@1  paused
     ...
   STEP   KIND   PASS  WHEN          +MS  WHAT
   start  Start  -     02:08:00.508    1  tickets, policy

   paused at fix since 2026-11-10T02:08:52.495+00:00: 1 task(s); aip resume 439478c79a714d6e --answers JSON
   ```

   and `aip runs --json --name ticket_triage` said `"entries": 1` for it. `--progress` had printed every one of those entries as they happened, and once `each_ticket` exited the same command printed 21 rows. The history (and so the server's `Entry` nodes and the step table) receives a `For`'s passes only when the loop exits; while the run is paused mid-loop the record says the run has done nothing since `start`, which is exactly when someone looks at it to decide how to answer. Whether the windowed audit queries also miss the in-flight passes I did not check while it was paused; `model-answers` showed `ticket_triage` only after the run was done. `docs/cli-json.md` says "Inside a `For` the entries are in pass order, not time order" but not that they are absent until the loop ends.

2. **A name whose every revision is retired is reported as nonexistent by `run`, `pull` and `get`.** With `@1` and `@2` both retired:

   ```text
   $ aip run billing_support --inputs '{"message": "hi"}'
   {"error": "invalid_input", "step": null, "message": "'billing_support' is not a folder or a bundle file, and http://127.0.0.1:8257 has no procedure by that name", "kind": "not_found", ...}
   $ aip info billing_support
   aip: not_found: billing_support has no live revision
   $ aip list
   billing_support        @-  2 revision(s)
   ```

   `info` has the right sentence; `run`, `pull` and `get` say the server "has no procedure by that name" when `aip list` shows it with two revisions. `aip list` also drops the description for that row, and `aip search refund` no longer finds it at all (search indexes the resolved revision), so the name quietly vanishes from discovery while its runs and `aip info name@rev` remain.

3. **`pin` and `retire` take different argument shapes.** `aip pin billing_support 1` is `name revision`; `aip retire billing_support 2` answers `aip retire: error: unrecognized arguments: 2` because retire is `name@revision`. The retire help's one-line hint (`ref  \`name@revision\``) is right, but a user who just typed `pin` will type `retire` the same way. Likewise unpinning: `aip pin billing_support none` gives `not_found: no revision none of billing_support`; the answer is `--clear`, which the bare `aip pin billing_support` does tell you.

4. **A pin beats a retire.** `aip retire billing_support@2`, then `aip pin billing_support 2` is accepted (`billing_support -> 2`), `aip list` shows `@2  2 revision(s)  pinned`, and `aip info billing_support` resolves to the retired revision. `docs/server-design.md` defines `name` as "the pinned revision, else the newest live one", so this is as specified, but retire is described as "stop the name resolving to a revision" and here the name resolves to it. Related and documented, still surprising: `aip run billing_support@2` runs a retired revision without a word that it is retired (step 24; `aip info billing_support@2` does not say so either).

5. **A stored audit query that returns a node is a 500.** `aip audit --save nodes-q --cypher 'MATCH (r:Run) RETURN r LIMIT 1'` stores fine; `aip audit nodes-q` prints `aip: internal: PydanticSerializationError: Unable to serialize unknown type: <class '<engine>._native.Node'>` (exit 1) and the server log gains a full traceback per call. The first thing anyone writes in Cypher is `RETURN r`. In the same area: `--save` accepts Cypher that does not parse (`MATCH (r:Run RETURN r` was `stored broken-q; run it with: aip audit broken-q`) and the error arrives only when it is run, prefixed `ProgrammingError:`; and `aip audit --debug` is not a flag (`run`/`resume` have it).

6. **`aip info --example-inputs` templates run as real inputs.** `aip run ticket_triage --inputs '{"policy": "<string>", "tickets": []}'` is accepted, iterates zero tickets and pauses at `summarize` with `"replies": []`; `aip run dynamic_policy --inputs '{"policies": [], "task": "<string>"}'` pauses at `draft` with `Task: <string>` in the prompt. Both are recorded on the server as runs of the published revision and sit in `aip runs --status paused` for good. The template looks like a form to fill; nothing says a placeholder left in place is a valid value, and the `info` summary for `ticket_triage` has no descriptions for its inputs to help (`policy  string` / `tickets  list`).

7. **Filters that silently match nothing.** `aip runs --name billing-support` (the folder's spelling) prints `no runs`; so does `--status bogus`. `aip audit model-answers --name billing-support` prints `[]`; `aip audit lineage --key nosuch` prints `[]`; `aip audit missing-fields --agent someone` returns the unfiltered rows because run filters do not apply to catalog queries (documented, but the command does not say so). `aip info billing-support` gives `not_found: no procedure 'billing-support'` with no nudge toward `billing_support`, and the hyphen-to-underscore change between folder and name is the first thing every user of the examples meets.

8. **Two voices for the same error.** `aip info nosuch` says `aip: not_found: no procedure 'nosuch'`; `aip pull nosuch` and `aip get nosuch` say `aip: 'nosuch' is not a folder or a bundle file, and http://127.0.0.1:8257 has no procedure by that name`; `aip run nosuch` wraps the latter in a JSON object with `"kind": "not_found"`. The second sentence is right for `run` and `info` (which take folders), odd for `pull` and `get` (which take only catalog refs).

9. **`aip config` names a file that is not on disk.** `aip config` says `its store is .../data/store.rl`; `ls data/` shows `store.cl` and the server log says `relate store at .../data/store.cl`. `docs/server-design.md` explains the engine pin; a user comparing the two lines sees a wrong path.

10. **`aip export --help` does not know about `runs`.** It shows only `aip export [-h] --out DIR [--force] BUNDLE` ("Write a bundle's program directory back"); the subcommand's help is `aip export runs --help`, discoverable only from the top-level command list. And `aip export runs billing_support` reports `wrote 7 run(s) of 3 procedure(s)`: one procedure, three bundles (two revisions and a draft).

11. **The step table hides a script's verdict.** In the finished `ticket_triage` table, `check  Execute  each_ticket 2  ...  scripts/policy_check.py -> passed` reads identically for the pass that passed and the two that failed; the failure is inferred from the `fix` row that follows or from `revise  Loop ... exit: until at head, 2 passes`. A decision's row shows `follows=false 0.92`; a script's answer-typed key shows its name only.

12. **`recorded: true` on a command that changed nothing.** Every refused `resume` (steps 16, 31) and the `not_paused` error carry `"recorded": true`. `docs/cli-json.md` says a refused answer "prints no line about recording at all", which is true of stderr; in the object it still claims a recording, and nothing in the record changed.

13. **Small presentation points.** `aip list` and `aip list --json` keep the source's continuation indentation inside the description (`"...drafted reply.\n   A structured decision..."`), so the listing's second line is indented three spaces further than the first and the JSON string carries them. `aip search` prints a bare score (`5.572`, `35.486`) with no scale. `aip publish broken` prints the diagnostic twice (once as a diagnostic line, once inside `does not compile (1 error(s)): ...`). `aip audit --json` is described as "the list of queries as JSON" though a query's rows are always JSON. The `--progress` line for a batched `Decide` shows `seconds: 0.68` on each of the three passes and no `batched` flag; only the step table says `one call for 3 passes`.

## Good

- The local server is invisible in the right way: `aip publish` started it in 0.59 s with one log line, every later command reused it, `aip server --local --stop` named the pid and the address, a second `--stop` said `no local server is running`, and `aip list` brought it back in 0.43 s with all 11 runs intact. `GET /health` tells the server from anything else on the port.
- Publish is idempotent and says so (`(already in the store)`); publishing a retired bundle brings its revision back; revision numbers and bundle ids are both shown.
- `aip runs` and `aip runs <id>` for a finished run are the best view of a run anywhere in the toolchain: nested passes (`each_ticket 2 / revise 0`), `answered by cli after 16.2s`, `one call for 3 passes`, the route's reason (`triage_decision.tone is angry; confidence 1.0 not below 0.9`), the loop's exit (`exit: until at summarize_check, 2 passes`), and `aip runs` falls back to the server when the run file is gone. `name@rev` and `name (draft)` in the NAME column settle "which revision ran" at a glance.
- Answer validation for a multi-task pause is specific: `task 0: reply is missing; task 0: answer is not a Produce key of draft; its keys are ['reply']`, `the pause has 2 tasks: the answers are an object keyed by task index ({"0": {...}, "1": {...}}) or a list in task order`, `there is no task 2; the pause has 2 tasks, 0, 1`, each with `missing_tasks`/`invalid_tasks`. The `hint` on every pause is the right shape to paste.
- `aip audit --save` validation is a model: kebab-case, not a built-in, no writing clause (`this one has DETACH`), `--save needs --cypher`; `$name`, `$limit` and `$bundles` bind in a stored query; `--delete cycles` says why not.
- `aip export runs` writes a store that answers the documented queries with no server (step 37), refuses to overwrite without `--force`, and its `--since` error shows the two accepted forms.
- `aip info` and the draft/published distinction in `aip runs` match the design doc exactly: a folder that compiles to a published bundle is recorded as that revision, an edited copy as `(draft)`.
- Error exits are consistent: 1 for every `aip:` message, 2 for argparse, one JSON object for `run`/`resume`.

## Top 5 changes, ranked

1. **Record a `For`'s passes as they happen, or show them.** A paused run inside a loop should list what it has done; if the history must stay in pass order, `aip runs <id>` and the server can read the frames' in-flight entries and mark them as such.
2. **One sentence for "no live revision" across `run`, `pull`, `get`, `info` and `list`** (and keep the row's description), and a "did you mean `billing_support`" when a hyphenated name misses.
3. **Make `retire` take `name revision` like `pin` (or `pin` take `name@rev`), refuse pinning a retired revision (or say it is retired), and print `retired` in `aip info name@rev` and in the run of one.**
4. **Serialize nodes and relationships in stored audit queries** (as maps with labels and properties, the way `GET /runs/{id}` does for records), validate Cypher at `--save`, and strip the engine's class and exception names from messages.
5. **Make `--example-inputs` placeholders fail validation** (or print them as a comment-bearing form), so the first thing a new user pastes does not create a permanent junk run; and give `aip export --help` a line about `runs`.
