# AIP 0.9 first-use report: `aip mcp` from a framework developer's own MCP client

Binary `aip 0.9.0 language 0.9`, MCP Python SDK `mcp 2.3.0`. `AIP_HOME`, `AIP_LOCAL_DATA`, `AIP_LOCAL_PORT=8267`, `AIP_SERVER=local` all pointed at a scratch dir; the decision model came from the user's own config and is not shown here. I read `docs/mcp.md`, `examples/agents/mcp-smoke/run.py`, `tests/test_mcp.py` and the plan's M1 comment first, then wrote my own client (`scratchpad/review-mcp/client.py`, 70 lines: `mcp.Client` over `StdioServerParameters(command="aip", args=["mcp"])` or a URL, `client_info=Implementation(name=..., version="0.1.0")`, every call with a progress callback, printing `structured_content` and the text block). 9 model-backed runs, 11 client processes, one HTTP server. The three published examples were `billing-support`, `dynamic-policy`, `ticket-triage` (`make_procedure@1` was already in the fresh store).

## Findings, ranked by how much they would confuse a framework developer

1. **A stdio client that does not forward its environment talks to a different AIP than the shell does, and `docs/mcp.md` does not say so.** #35: my first client, written from `docs/mcp.md` alone (`StdioServerParameters(command="aip", args=["mcp"])`), got `no_server` while `aip search` in the same shell worked, because the MCP SDK starts the child with a minimal environment and `aip mcp` then read the user's real config (`server: none`) and the default `AIP_HOME`. The doc says "An MCP client's configuration names the command and nothing else" and shows `{"mcpServers": {"aip": {"command": "aip", "args": ["mcp"]}}}` with no `env`. The fact is stated only in the smoke example's docstring ("The whole environment is passed on") and the M1 plan comment ("A stdio client must pass the environment on"). A developer who sets `AIP_SERVER`/`AIP_HOME`/`AIP_DECISION_MODEL_KEY` in `.env` and sees `no_server` or `no_decision_model` has nothing in `docs/mcp.md` to tell them why. I could not verify whether that call wrote anything under `~/.aip` (a `search` with `no_server` should not).

2. **Folder name and published name differ (`billing-support` vs `billing_support`) and the not-found messages do not bridge them, nor agree with each other.** #9, #16, #29: `describe billing-support` says `not_found: no procedure 'billing-support'`; `run`/`pull` say `'billing-support' is not a folder or a bundle file, and http://127.0.0.1:8267 has no procedure by that name`. `describe`'s message repeats its `kind` as a prefix; `run`'s mentions folders and bundle files for a bare name. For a bad revision `describe` says `no revision 7 of billing_support` while `pull billing_support@3` says `no procedure by that name`. A model reading these would conclude two different things about the same catalog. Note too that `aip publish examples/language/billing-support` prints `billing_support@1`, so the underscore is discoverable only from publish's output or `search`.

3. **Argument-shape mistakes are MCP errors with raw pydantic text, contrary to "Only a bug in the server is an MCP error".** #5 (`search {}`), #34 (`answers: "just a string"`): `isError: true`, `structured_content: null`, text `Error executing tool search: 1 validation error for searchArguments / query / Field required [type=missing, input_value={}, input_type=dict] / For further information visit https://errors.pydantic.dev/2.13/v/missing`. The design argument in `docs/mcp.md` (a framework that raises on tool errors must not lose a pause) is honored for pauses and run errors, but the same framework will raise here, and the message is the validator's, not AIP's. The `answers` case is the likelier one: a model that hands `resume` a JSON string instead of an object gets a pydantic dump instead of `invalid_output`.

4. **Progress notifications name the inner pass only, so two different tasks look like one step repeated.** #27: the `fix` resume produced `(1, 'Task_Agent fix (pass 0)'), (2, 'Task_Agent fix (pass 0)'), (3, 'Execute check (pass 0)'), (4, 'Loop revise (pass 0)'), (5, 'Execute check (pass 0)'), (6, 'Loop revise (pass 1)')`. The two `fix` entries are ticket 0 and ticket 1 (`each_ticket` pass 0 and 1), each at `revise` pass 0; the notification shows only `pass 0`. `total` is always `None`, so a progress bar cannot be drawn; and for a run that pauses, the stream simply ends at the step before the pause (`Route by_tone`, #18) with no "paused at reply" message, so a client that shows progress has to read the result to learn why the stream stopped.

5. **`search` has no floor and an undocumented key.** #4: a nonsense query returns two hits at 0.76 and 0.63 against 24.5 for a real match; `docs/mcp.md` lists `name, revision, score, description` and the object also has `bundle_id`. The tool description says "best first", which a model will read as "the first is right". Nothing says what scale `score` is on or when a hit is not worth taking. (The `instructions` say "Use a procedure when one fits the task", which puts the judgment on the model with no number to go by.)

6. **`pull` of a freshly published name says `fetched: false`.** #14: the first `pull billing_support` I ever made answered `fetched: false` because `aip publish` on the same machine had already cached the bundle. The tool description says `fetched` is "whether it was fetched now or already there"; true to the letter, but a developer testing "does pull work" on a one-machine setup sees `false` on every call and cannot tell a working pull from a no-op. `pull` with a ref echoes `ref: "billing_support"`; `pull {}` writes `ref: "billing_support@1"`, so the same bundle has two `ref` spellings depending on how it was asked for.

7. **`compile`'s `output` and `folder` are looser than documented.** #11: `output` "a path ending in `.rl`" accepted `bs.bundle` and wrote 73728 bytes to it; `describe`/`run` would later need to recognize that file. #13: `folder` accepted the `procedure.aip` file path. #12: a missing folder gives `message: "/nonexistent/folder: [Errno 2] No such file or directory: ..."`, Python's text where `run` on the same path (per `tests/test_mcp.py`) gives a plain `not_found`.

8. **`describe.result` lists keys a `done` result may not have.** #6 vs #17: `describe billing_support` says `result {message, queue, reply, ticket_id}`; the angry run's `result` is `{message, ticket_id, queue}` and the calm run's is `{message, reply}`. Nothing in `describe` marks `reply`, `queue`, `ticket_id` as route-dependent. A framework that builds a typed result from `describe` will find keys missing.

9. **`aip runs` is "newest first" by `UPDATED`, not `STARTED`.** #41: the `ticket_triage` run (started 02:09:33, resumed last at 02:10:51) heads the list above runs started a minute later. Help says "Runs, newest first". With the two columns side by side it is readable, but a script taking row 0 as "the run I just started" gets the wrong one when an older run was resumed.

10. **Error objects differ in which keys they carry.** `not_found`/`no_server`/`compile_error` have `kind`; `invalid_input` for inputs (#28) has `step: "start"`, `missing`, `invalid`, `pass`, `passes` and no `kind`; the unknown-run-id error (#32) has neither `kind` nor `step`. `docs/cli-json.md` describes this, but a framework that switches on `kind` gets `None` for a bad run id and for bad inputs alike.

11. **The `fix` task does not say what `check` found.** #26: after two reasonable replies, both went to `fix` with `prompt: Revise the reply so it quotes the policy correctly.` and `state {reply, policy}`; the script's verdict (what was missing) is not in the task. I quoted the whole policy sentence verbatim to get past it. This is the example's design rather than the MCP layer, but it is the first multi-task loop a developer will drive through `resume`, and it looks like the runtime withholding information.

12. **Identity: name without version, one `session` per HTTP server process.** #40, #43: the record holds `agent: my-framework` and `aip runs --agent my-framework@0.1.0` finds nothing; my `Implementation(version="0.1.0")` is nowhere. For the filter, the name alone is what I would type, so this matched my expectation; what I would miss later is "which version of my framework produced this run" when debugging a regression, and no field holds it. Two HTTP clients that pass no `session` share the server's `mcp-733e0779` (#38), as `docs/mcp.md` says; a developer who forgets `session` on a shared `--http` server gets every caller's runs under one session. `user` is `null` under the local server (`aip runs` shows `user -`), while `docs/mcp.md` says `user` "is the server token's name, as everywhere"; it does not say the local server has none.

13. **Small text points.** `describe` key order differs by name (alphabetical) and by path (source order); harmless for JSON, visible in the text block. `ticket_triage`'s `input_descriptions` are two empty strings, so a model gets `policy: ""`. The `instructions` text tells the model "one answer per task: an object with exactly the keys of the task's `answer_with`" and leaves the list / index-keyed forms to the `resume` description and the `hint`; a model that reads only `instructions` will make mistake #22 once (the refusal then says exactly what to do).

## What worked well

- **Every tool answered with one object, the same in `structured_content` and in the text block**, and pauses, refused answers and unusable targets all came back as results with a first key that said which (`paused` / `done` / `error`). My client never had to special-case a transport error for an application outcome.
- **The `hint` line is right every time**: `answer with {"reply": <string>}` for one task, `answer all 2 tasks at once, by index: {"0": {"reply": <string>}, "1": ...}` for two; following it literally worked on the first try.
- **Answer validation is strict and specific.** #22-#25, #33: an extra key (`confidence`), a wrong key (`answer`, `draft`), a wrong type (`42`), a missing task, a surplus task and a bad index were each refused with the task index, the offending key and the allowed keys, plus `missing`, `invalid`, `missing_tasks`, `invalid_tasks` as lists. The pause stood and the next answer went through. (The earlier CLI review's "extra key silently accepted" is gone.)
- **Input validation on `run` is equally exact**: `msg is not an input of this procedure; the inputs are ['message']`, `expected a string, got an integer`.
- **A program that does not compile fails `run` with the compiler's `diagnostics`** in the result (`code`, `severity`, `message`, `file`, `line`, `column`, `end_line`, `end_column`, `step`), as the doc promises.
- **Identity lands where the doc says**: `agent` is the `clientInfo.name` (`my-framework`, `http-framework`, `other-framework`), `mcp` when none; `session` is the `run` argument when given (`mf-billing`, `hf-1`) else `mcp-<8 hex>`; `answered_by {agent, session}` is on every `Task_Agent` entry I answered, and `aip runs <id>` renders it as `answered by my-framework after 0.0s`. `aip runs --agent`, `--session` and the human step view (`+MS`, `WHAT`, `(by jev-1.14.0)`) make a run I drove over MCP readable from the terminal.
- **Runs started over MCP are ordinary runs**: the `run_file` path is in every result, `aip runs <id>` reads it, and the stopped local server restarted on demand from the first MCP call in 0.27 s.
- **HTTP is the same contract** at `/mcp`, up in under half a second, two clients kept apart by name, bad paths answered with proper 404/400 JSON-RPC.
- **Speed**: connect 0.3 s, model-backed `run` 0.12-0.64 s, every error path under 0.03 s. Nothing here needed a timeout.

## What I could not verify

- Whether the no-environment client (#35) touched `~/.aip` or the user's config; its only call was a `search` that returned `no_server`.
- `workdir`: none of the three procedures' scripts write files, so #20's `workdir` and the `--http` server's cwd could only be read from the record, not from disk.
- What a 1.x MCP SDK client, or a Claude Desktop / Cursor style `mcpServers` config, does against this 2.x server; I used `mcp 2.3.0` only.
- Any authentication on `--http`; the doc says there is none and I did not add any.
- Behaviour with no decision model (`no_decision_model`), `bundle_tampered`, and whether progress `total` is ever set.
- Whether the duplicate `Task_Agent fix (pass 0)` notifications (#4) could be told apart by a progress `token` or field my callback did not receive; the SDK's callback gave me `(progress, total, message)` only.
